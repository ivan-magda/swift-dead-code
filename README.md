# swift-dead-code

Find and remove dead code in SwiftPM packages and Xcode apps, with the same results on every
run. `swift-dead-code` is a command-line tool that orchestrates the compiler, your build
system and [Periphery](https://github.com/peripheryapp/periphery): it never deletes anything
itself, and it never writes into your working tree. Deletions leave it as a patch or a list
of findings that you, or an agent with the bundled skill, verify and apply.

| Command | Builds? | Finds |
| --- | --- | --- |
| `check` | no, seconds | target dependencies no file imports; files and asset catalog entries nothing names |
| `scan` | yes | unused declarations from Periphery, with and without test code, plus a triage report |
| `triage` | no | the scan's report again, from two Periphery JSON files |
| `baseline` | no | Periphery findings in product code that your recorded backlog lacks |
| `prune-imports` | yes, one build per module | imports the compiler proves removable, as a patch; `--check-only` lists files that borrow imports |
| `describe` | no | the targets, test code and dependencies the tool sees |
| `init` | no | a starter `.deadcode.yml` |

It reads SwiftPM packages (`swift package dump-package`), Xcode projects and workspaces
(including projects generated by XcodeGen or Tuist, local Swift packages, synchronized
folders, xcconfig files and CocoaPods workspaces), and builds Xcode projects with
`xcodebuild` for the simulator with code signing off.

## Install

You need macOS 14 or later, Swift 6.2 or later, and for `scan` the last MIT release of
Periphery, 3.8.0:

```bash
brew install periphery
```

Periphery's repository is archived; 3.8.0 is its last open-source release, and
[Periphery Pro](https://periphery.pro) continues it commercially (it needs an account). The
triage notes were checked against 3.8.0, so `scan` refuses another version unless you set
`periphery.version` in `.deadcode.yml`.

Once the repository is published, install the tool with
[Mint](https://github.com/yonaskolb/Mint), which builds the `swift-dead-code` product
(not verified yet):

```bash
mint install ivan-magda/swift-dead-code
```

Or build it from a clone:

```bash
swift build -c release
cp .build/release/swift-dead-code /usr/local/bin/
```

A Homebrew formula would build the same way (`swift build -c release --disable-sandbox` and
install `.build/release/swift-dead-code`); none is published yet.

In a SwiftPM project you can also add this package as a dependency and run the command
plugin. The plugin runs `swift`, `git` and `periphery`, so it needs the sandbox off:

```bash
swift package --disable-sandbox dead-code check
```

## Set up a project in a few minutes

1. Print a starter configuration and review it:

   ```bash
   swift-dead-code init > .deadcode.yml
   swift-dead-code describe
   ```

   `describe` lists every target with its role (product, test, test support), module name and
   dependencies. If a target is missing, a test helper target counts as product code, or a
   module name is wrong, fix `.deadcode.yml` before trusting any finding. Xcode projects must
   name the schemes to build; `init` lists the shared ones. For XcodeGen or Tuist, generate
   the project first: the tool reads the generated `.xcodeproj` and never runs the generator.
   For CocoaPods, run `pod install` first.

2. Run the quick gate and decide each finding:

   ```bash
   swift-dead-code check --report
   ```

   Delete what is dead. Keep the rest in the allowlist, each entry with a reason; an entry that
   no longer matches a finding fails the gate, so the list cannot go stale. For a library
   whose public API others use, add `--retain-public` to `periphery.arguments`, so `scan`
   treats public declarations as the contract they are.

3. Add the gate to your lint script or CI. It needs no build and exits non-zero on a new
   finding, with compiler-style `path:line:col: error:` lines:

   ```bash
   swift-dead-code check
   ```

4. Run the deep analysis weekly, as [`examples/github-workflow.yml`](examples/github-workflow.yml)
   does: `scan`, then `baseline` against your recorded backlog, then
   `prune-imports --all --modules deps --strict`.

   ```bash
   swift-dead-code scan --output .build/dead-code/scan
   swift-dead-code baseline .build/dead-code/scan/all.json .build/dead-code/scan/prod.json
   swift-dead-code prune-imports --work .build/dead-code/prune --all --modules deps
   ```

   `scan` and `prune-imports` copy the project into their output directory and build there.
   Reuse one directory per command, so reruns build incrementally. Both take a machine-wide
   lock: two builds at once finish later than the same two in sequence.

## Configuration

Every field of `.deadcode.yml` is optional; unknown keys are errors, so a typo cannot fall
back to a default silently. [`examples/`](examples) has configurations for a SwiftPM
package, an Xcode app and a CocoaPods workspace.

```yaml
project:
  kind: auto                     # auto | swiftpm | xcode
  path: App.xcworkspace          # Xcode: the workspace or project
  schemes: [App]                 # Xcode: schemes to build and scan
  configuration: Debug           # default: each scheme's own
  destination: "generic/platform=iOS Simulator"
  build_arguments: []            # extra swift build / xcodebuild arguments

test_support: [AppTestSupport]   # targets (or path globs) that count as test code
exclude: ["Generated/**"]        # generated or vendored code no check reports on
module_names:                    # a product or pod whose modules have other names
  Firebase: [FirebaseCore, FirebaseAnalytics]

check:
  conventional_paths: ["tools/"] # found by location; added to the defaults
  conventional_files: ["*.env.example"]   # found by name; added to the defaults
  not_references: ["docs/research/"]      # neither checked nor counted as mentions
  min_stem_length: 4
  assets: true

allowlist:                       # every entry needs a reason
  - file: docs/assets/demo.png
    reason: linked from the website
  - asset: App/Assets.xcassets/achievement-*.imageset
    reason: loaded by computed name in AchievementView
  - dependency: {target: App, module: Analytics}
    reason: linked for its load-time registration

periphery:
  version: 3.8.0
  baseline: .deadcode/periphery-baseline.txt
  retain_codable_properties: true
  retain_equatable_properties: true
  arguments: []                  # extra periphery scan options

prune:
  toolchain_modules: [Testing, Synchronization]   # tried by --modules deps
  platform_modules: []           # added to the never-pruned Foundation/OS list
  keep_modules: []               # never pruned

docs:
  contracts: [docs/ARCHITECTURE.md]   # where the project documents its contracts

triage:
  seam_name_pattern: 'For(?:Testing|Tests)\b'

builds:                          # several builds, scanned together
  - name: ios
    schemes: [App]
    destination: "generic/platform=iOS Simulator"
  - name: macos
    schemes: [MacApp]
    destination: "generic/platform=macOS"
    for_testing: false           # build without the scheme's test targets
```

How the checks decide:

- **Dependencies.** Imports are read with SwiftSyntax in every `#if` branch, so a dependency
  used on one platform counts. `@_exported`, `@testable`, `@_spi`, access-level and scoped
  imports count, `#externalMacro(module:)` counts for macro targets, and Objective-C sources'
  `@import` and `#import <Module/...>` count. Xcode app extensions, apps and bundles are
  embedded rather than imported, so they are not checked; neither are plugin targets. A
  framework target that a string literal of the dependent target names counts too: that is
  how an embedded, unlinked framework is loaded with `dlopen` or `NSClassFromString`. A
  dependency also stays when a target that depends on this one, directly or through others,
  imports it without declaring it: that target gets the module through this one.
- **Files.** A tracked file is used when another tracked text file contains its stem (four
  characters or more), its whole name, a string literal that is exactly a shorter stem
  (`"atp"` in `url(forResource: "atp", withExtension: "rss")`), or a pattern such as
  `results/run-*.md` that matches it; `$(VAR)` and `${VAR}` in a path match anything.
  `@2x`, `~ipad` and `~dark` variants count by their base name. Project membership
  (`project.pbxproj`) is not a use; build settings such as `INFOPLIST_FILE`, xcconfig files,
  and Run Script phases' scripts and input and output paths are. Swift files no target
  compiles are candidates too, except inside nested packages and projects.
- **Assets.** An `imageset`, `colorset`, `symbolset` or `dataset` is used when a file outside
  asset catalogs names it, the identifier Xcode generates for it (`my-icon` → `myIcon`), or
  the part of its name before a digit, `-` or `_`, which catches names code builds at runtime.
- **Periphery scans.** One run with tests, one with test code left out of the index, so
  declarations only tests use form their own section. The tool writes its own Periphery
  configuration: a project's `.periphery.yml` is ignored, so move its options to
  `periphery.arguments`. Results hold only for what was built; `builds` scans several
  platforms or configurations into one index, and a declaration any of them uses stays.
  Targets that share a module name, such as an iOS and a macOS app both named after the
  product, merge in that index: Periphery can lose one copy's calls, differently from run to
  run, so findings in a type both declare carry a note and need a check by hand.

## The agent skill

[`skills/removing-dead-code/SKILL.md`](skills/removing-dead-code/SKILL.md) covers what the tool
cannot decide: the verdict on each Periphery finding (seam, contract, AMBIGUOUS), a brief for an
independent researcher before each deletion group, and the completeness sweep that gates the
pull request. It calls the CLI and does not repeat its logic.

Install it for Claude Code in one project, or for every project:

```bash
cp -R skills/removing-dead-code <project>/.claude/skills/
cp -R skills/removing-dead-code ~/.claude/skills/
```

Codex and other agents that read `.agents/skills/` take the same directory. To ship it through
a plugin marketplace such as
[claude-code-marketplace](https://github.com/ivan-magda/claude-superpowers), copy the
directory to `plugins/swift/skills/removing-dead-code/` (or a new `plugins/swift-dead-code/`
with its own `.claude-plugin/plugin.json`), add the plugin to `.claude-plugin/marketplace.json`
if it is new, and bump the plugin version.

## Beyond static analysis

Static analysis sees only code that was compiled and references the index can record. Code
that is reachable but never runs in production needs runtime data: the open-source
[Reaper](https://github.com/getsentry/reaper-ios) SDK, from Emerge Tools and now at Sentry,
reports which Swift and Objective-C types production sessions use. It complements this tool;
the tool does not use it.
