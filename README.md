# swift-dead-code

[![CI](https://github.com/ivan-magda/swift-dead-code/actions/workflows/ci.yml/badge.svg)](https://github.com/ivan-magda/swift-dead-code/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

A command-line tool for finding unused code, imports, dependencies, files, and assets in
SwiftPM packages and Xcode projects.

Use `check` to find unused dependencies and resources without a build. Use `scan` to find
unused declarations with [Periphery](https://github.com/peripheryapp/periphery), or
`prune-imports` to produce a patch of imports you can remove. You review and apply the
changes; the tool does not delete code or edit your source files.

Supported projects include SwiftPM packages, Xcode projects and workspaces, local Swift
packages within Xcode projects, and CocoaPods workspaces. Xcode support includes
synchronized folders, xcconfig files, and projects generated by XcodeGen or Tuist.

<a id="install"></a>

## Installation

Requires macOS 14 or later. Building from source requires Swift 6.2 or later.

### Homebrew

```bash
brew install ivan-magda/tap/swift-dead-code
```

### Mint

```bash
mint install ivan-magda/swift-dead-code
```

### Prebuilt binary or source

Download `swift-dead-code-<version>-macos.zip` from
[Releases](https://github.com/ivan-magda/swift-dead-code/releases). Each release includes a
universal macOS binary and a `checksums.txt` file with its SHA-256 checksum.

To build from a clone:

```bash
swift build -c release
cp .build/release/swift-dead-code /usr/local/bin/
```

### Periphery

The `scan` command requires Periphery 3.8.0, the last MIT-licensed release. Download and
verify that version:

```bash
curl -fsSLO https://github.com/peripheryapp/periphery/releases/download/3.8.0/periphery-3.8.0.zip
echo "07d4e286e31dd79164df39097e0b59f533c94badbe18158464a455ea88a166d7  periphery-3.8.0.zip" \
  | shasum -a 256 --check
unzip periphery-3.8.0.zip -d periphery-3.8.0
```

Add the extracted directory to your `PATH`. The triage notes target this version; `scan`
rejects other versions unless you override `periphery.version` in `.deadcode.yml`.

### SwiftPM command plugin

The [command plugin](https://github.com/ivan-magda/swift-dead-code-plugin) bundles the
release binary and Periphery 3.8.0. Add it to your package's dependencies:

```swift
.package(url: "https://github.com/ivan-magda/swift-dead-code-plugin", from: "0.1.0"),
```

Run the plugin with the sandbox disabled so it can invoke `swift`, `git`, and `periphery`:

```bash
swift package --disable-sandbox dead-code check
```

## Quick start

Run these commands from your project root.

### 1. Configure the project

```bash
swift-dead-code init > .deadcode.yml
swift-dead-code describe
```

Review `.deadcode.yml` and the `describe` output. Check target roles (product, test, or test
support), module names, and dependencies. Correct missing targets or wrong roles before
reviewing findings.

For Xcode projects, choose the schemes to build; `init` lists the shared schemes. Run
`xcodegen generate` or `tuist generate` before setup if you use a project generator, or
`pod install` for CocoaPods. The tool reads the resulting project files.

For a library with public API that other packages use, add `--retain-public` to
`periphery.arguments` so the scan keeps those declarations.

### 2. Review findings

```bash
swift-dead-code check --report
```

Remove unused code and resources. For findings you need to keep, add an `allowlist` entry
with a reason. The check rejects stale entries that no longer match a finding, duplicate
entries, and entries without reasons.

### 3. Add the check to CI

```bash
swift-dead-code check
```

This command needs no build. It exits with a nonzero status for findings outside the
allowlist or invalid allowlist entries, and prints diagnostics as `path:line:col: error:`.
Use `--report` for review: it prints all findings, including allowlisted ones, without
failing on them.

### Scan declarations and prune imports

Scanning declarations and pruning imports require builds and take longer than `check`:

```bash
swift-dead-code scan --output .build/dead-code/scan
swift-dead-code baseline .build/dead-code/scan/all.json .build/dead-code/scan/prod.json
swift-dead-code prune-imports --work .build/dead-code/prune --all --modules deps
```

Review `.build/dead-code/scan/report.md` for unused declarations and code that tests alone
use. The `baseline` command fails on product-code findings missing from your recorded
backlog. After reviewing the findings you intend to keep, use `baseline --write` to replace
the baseline with the current product-code findings.

The import pruner writes `.build/dead-code/prune/prune.patch`. Review the patch before
applying it. Add `--strict` to make removable imports fail CI. The
[example GitHub Actions workflow](examples/github-workflow.yml) runs these checks on a
weekly schedule.

Both `scan` and `prune-imports` build in a copy inside their output directory. They also copy
each local package outside the project root that the build needs, such as
`.package(path: "../Shared")` or an Xcode local package reference, to the same place relative
to the project. Reuse a directory for each command to preserve the build cache. A
machine-wide lock serializes these builds. Xcode builds use a simulator destination by
default, with code signing off.

## Commands

| Command | Builds the project | Purpose |
| --- | --- | --- |
| `check` | No | Find unused target dependencies, files, and assets. |
| `scan` | Yes | Run Periphery with and without test code and write a triage report. |
| `triage` | No | Generate a triage report from two existing Periphery JSON scans. |
| `baseline` | No | Check product-code findings against a recorded backlog. |
| `prune-imports` | Yes | Test import removals and write a patch. Use `--check-only` to find files that rely on another file's imports. |
| `describe` | No | Print targets, module names, roles, and dependencies. |
| `init` | No | Print a starter `.deadcode.yml`. |

Run `swift-dead-code <command> --help` for options. Results go to stdout; diagnostics and
progress go to stderr. Reports use stable ordering for comparison between runs.

## Configuration

Place `.deadcode.yml` in your project root. All fields are optional; unknown keys are
errors. See [`examples/`](examples) for SwiftPM, Xcode, and CocoaPods configurations.

This example shows the available settings. Choose paths, schemes, and builds for your
project:

```yaml
project:
  kind: auto                       # auto | swiftpm | xcode
  path: App.xcworkspace             # Xcode workspace or project
  schemes: [App]                   # Xcode schemes to build and scan
  configuration: Debug             # default: each scheme's configuration
  destination: "generic/platform=iOS Simulator"
  build_arguments: []              # extra swift build / xcodebuild arguments

test_support: [AppTestSupport]     # target names or path globs for test support code
exclude: ["Generated/**"]          # paths to exclude from findings
module_names:                      # product or pod names mapped to importable modules
  Firebase: [FirebaseCore, FirebaseAnalytics]

check:
  conventional_paths: ["tools/"]   # add to the default paths tools discover by convention
  conventional_files: ["*.env.example"] # add to the default filenames
  not_references: ["docs/research/"]    # skip checks and references from these paths
  min_stem_length: 4
  assets: true

allowlist:                         # give each entry a reason
  - file: docs/assets/demo.png
    reason: linked from the website
  - asset: App/Assets.xcassets/achievement-*.imageset
    reason: loaded by computed name in AchievementView
  - dependency: {target: App, module: Analytics}
    reason: linked for its load-time registration

periphery:
  version: 3.8.0
  baseline: .deadcode/periphery-baseline.txt
  retain_codable_properties: true
  retain_equatable_properties: true
  arguments: []                    # extra periphery scan options

prune:
  toolchain_modules: [Testing, Synchronization] # include with --modules deps
  platform_modules: []             # extend the default Foundation and OS module exclusions
  keep_modules: []                 # exclude these modules from pruning

docs:
  contracts: [docs/ARCHITECTURE.md]  # documents describing API contracts

triage:
  seam_name_pattern: 'For(?:Testing|Tests)\b'

builds:                            # scan across multiple builds
  - name: ios
    schemes: [App]
    destination: "generic/platform=iOS Simulator"
  - name: macos
    schemes: [MacApp]
    destination: "generic/platform=macOS"
    for_testing: false             # omit the scheme's test targets
```

## How the checks decide

### Dependencies

The dependency check reads Swift imports with SwiftSyntax across all `#if` branches. It
counts `@_exported`, `@testable`, `@_spi`, access-level, and scoped imports, plus
`#externalMacro(module:)` references for macro targets. For Objective-C, it counts
`@import` and `#import <Module/...>` in sources, bridging headers, and headers they include
through relative paths.

The check skips plugin targets and dependencies on apps, app extensions, and bundles,
which Xcode embeds rather than imports. A string literal in a dependent target that names
a framework target counts as a reference, covering loads through `dlopen` or
`NSClassFromString`.

The check preserves dependencies that provide access to modules through the dependency
graph. For example, if target A imports a module through B, removing B must leave A another
path to that module. It evaluates each candidate with earlier findings removed, so the
reported removals preserve those paths as a group.

### Files

The file check looks for references to a tracked file in other tracked text files. It
counts:

- A filename or a stem of at least `min_stem_length` characters (four by default).
- An exact string literal for a shorter stem, such as `"atp"` in
  `url(forResource: "atp", withExtension: "rss")`.
- A matching path pattern, such as `results/run-*.md`. Variables in paths, including
  `$(VAR)` and `${VAR}`, match any value.

Variants such as `@2x`, `~ipad`, and `~dark` share their base name for matching. Xcode project
membership alone does not count as use. Build settings such as `INFOPLIST_FILE`, xcconfig
files, Run Script bodies, and script input and output paths do count.

Swift files outside any target are candidates, except those in nested packages and
projects. The check skips files that tools discover by name or location, including
licenses, lockfiles, `module.modulemap`, Core Data model bundles, and `Pods/`. See
[`Defaults.swift`](Sources/DeadCodeKit/Configuration/Defaults.swift) for the full list.

### Assets

The asset check covers `imageset`, `colorset`, `symbolset`, and `dataset` entries. A file
outside asset catalogs must reference the asset's name, its generated Swift identifier
(`my-icon` becomes `myIcon`), or the prefix before a digit, `-`, or `_`. Prefix matching
accounts for names your code constructs at runtime.

### Periphery scans

The scan runs Periphery twice: once with tests and once with test code excluded from the
index. The report separates production declarations that tests alone use from other
findings.

`scan` supplies its own Periphery configuration and ignores the project's `.periphery.yml`.
Move those options to `periphery.arguments`. Results cover the platforms and configurations
you build. Use `builds` to cover several; a reference in any of them keeps the declaration.

The scan reports none of the declarations in local packages outside the project root, but it
keeps those packages in the index, so a call they make into the project counts. A package that
contains the project gets reported with it: an example app that depends on its library
through `../..` gets findings in the library too.

Targets that share a module name can produce false positives in a merged index. For these
projects, the scan uses an index per build and checks findings against each build that
contains the declaration. It keeps a finding if all relevant builds report the finding or
the declaration as unused. The report flags findings in types that both targets declare
for further review.

### Imports

The import pruner removes candidates in a project copy, one module at a time, and builds to
check the result. It keeps imports that any configured build needs, including imports a
file relies on through another file in its target. With `--all` or `--base`, it skips test
code unless you add `--include-tests`.

The pruner skips imports inside `#if` blocks. It excludes Foundation and platform modules
by default; `--include-platform` includes them.

An Xcode scheme builds its targets and their dependencies. The pruner skips and lists files
that no configured build compiles. In `--check-only` mode, an unchecked target fails the
command. Add a scheme or build that covers the target before rerunning it.

## Agent skill

The bundled [removing-dead-code skill](skills/removing-dead-code/SKILL.md) guides a coding
agent through reviewing findings and applying removals. It covers test seams, public
contracts, ambiguous findings, an independent review before each deletion group, and a
final sweep for code or resources left unused by the changes.

Install it for your project with the [skills CLI](https://github.com/vercel-labs/skills):

```bash
npx skills add ivan-magda/swift-dead-code
```

Add `-g` to install it for all projects. You can copy `skills/removing-dead-code` into
`.claude/skills/` for Claude Code or `.agents/skills/` for Codex, either in your project or
your home directory.

## Limitations

Review findings before removing code. Static analysis covers compiled code and references
available in the index. It cannot establish whether reachable code runs in production.
For runtime usage data, [Reaper](https://github.com/getsentry/reaper-ios) reports which Swift
and Objective-C types production sessions use. This project has no Reaper integration.
